# 管理员自由调整站位 — 设计规格

日期：2026-09-20
状态：已确认

## 1. 背景与目标

排表采用「自由站位」：玩家各自往空格放自己的角色。问题在于**并非所有玩家都具备合理排表的能力**，导致站位不合理（输出扎堆、缺奶、划水混入等）。

目标：为**管理员**提供完整的位置调整能力，在不改变普通玩家现有习惯的前提下，让管理员可以：

- 往任意空格放入**任意玩家**的角色
- 对已占位格**换人**（撤下原角色、放入新角色）
- **拿起**一个角色并放到另一个格子（移动），或与目标格角色**对调**（支持跨波次）

## 2. 权限模型（普通玩家现状保持不变）

| 能力 | 普通玩家 | 管理员 |
|---|---|---|
| 空格放自己的角色 | ✅（未锁定） | ✅ 任意玩家角色 |
| 空格放别人的角色 | ❌ | ✅ |
| 已占位格换人（自动撤下原角色） | ❌ | ✅ |
| 拿起 → 点目标格 移动/对调 | ❌ | ✅ |
| 撤下 / 改职责 | 仅自己的格 | 任意格 |
| 锁定后编辑 | ❌ | ✅（现状） |

- 普通玩家所有既有限制（只能用自己的角色、只能操作自己的格、锁定后不可编辑）**原样保留**，本次不改。
- 管理员在锁定时依旧可编辑（沿用现有 `_can_edit` 语义）。

## 3. 后端改动

### 3.1 `fill` 接口改造（`backend/app/routers/raids.py`）

现状：`POST /api/raids/{rid}/slots/{slot_id}/fill` 要求格子必须为空（`slot.character_id is not None` → 400），非管理员只能用自己角色。

改造：

- **管理员**：
  - 允许 `body.character_id` 为任意玩家的角色（放开「只能使用自己的角色」）
  - 允许往**已占位**格直接放入（视为「换人」：先自动清空该格原角色，再放入新角色）
- **普通玩家**：所有限制保持不变（格子必须为空、只能用自己的角色）
- 现有 `replace: true` 冲突替换逻辑（同一角色已在其他格 / 同玩家同波已占 → 自动撤下冲突格）对管理员同样生效
- 请求体中 `replace` 字段语义不变（前端始终传 `true`）

### 3.2 新增 `POST /api/raids/{rid}/slots/{slot_id}/move`

body：`{ "target_slot_id": int }`

语义（原子操作，任何校验失败整体回滚 400）：

- **前置**：
  - 仅管理员可用（非管理员 → 403）
  - 源格（`slot_id`）必须已占位（否则 400「该格为空」）
  - 目标格（`target_slot_id`）与源格同属一个攻坚（否则 404「格子不存在」，沿用 fill 的判定方式）
  - 目标格不允许等于源格（否则 400）
- **目标为空**（move）：源格角色+职责搬到目标格，源格清空
- **目标已占位**（swap）：两格角色+职责互换
- **受影响方**：
  - 源格所属小队、目标格所属小队（同一小队时只校验一次）——走 `_raise_if_hard` 组成规则（主奶超限恒硬性；满员 4/4 无划水时组成问题硬性）
  - **同波同玩家限一人**：跨波 move/swap 后，受影响波（源波与目标波）内**任一玩家不得出现两个角色**；swap 需**双向**检查（双方各自进入对方波次）。违反 → 400「同一波次中一个玩家只能上一个角色」。同波内对调集合不变，天然满足，无需额外检查
- **副作用**：所有受影响 slot 的 `version += 1`；move 时被搬空的源格沿用现有 `_clear_slot`（`updated_by`/`updated_at` 置空），被填充的目标格记录 `updated_by = 管理员`、`updated_at = now`；swap 时两格都记录 `updated_by = 管理员`、`updated_at = now`（`updated_by` 仅作审计，不参与权限判定，见 3.4）
- **返回**：`FillResponse` —— `slot` = 目标格、`warnings` = 受影响小队组成警告、`removed_slots` = 被清空的源格（move 时；swap 为空）
- **广播**：复用现有 WS 事件，前端无需新增事件类型
  - move：目标格 `slot:filled` + 源格 `slot:removed`
  - swap：两格各 `slot:filled`

### 3.3 新增 `GET /api/admin/characters`（仅管理员）

返回全部玩家及其角色，供选人弹窗使用：

```json
[
  { "user": { "id": 1, "nickname": "小红", "username": "hong", "is_admin": false },
    "characters": [ { "id": 11, "name": "剑魂·傲天", "job_title": "剑魂", "class_type": "输出", "fame": 52000, ... } ] }
]
```

- 结构复用现有 `UserOut` 与 `CharacterOut`
- 按玩家分组、玩家内按角色 id 排序
- **过滤掉没有任何角色的玩家**（减少选择器噪音；前端无需处理空态分支）

### 3.4 非管理员「自己的格子」判定统一改为按角色归属

现状：`remove_slot` / `change_duty` 对非管理员用 `slot.updated_by != user.id → 403` 判定「只能操作自己的格子」；删波次（`delete_wave`）也用 `s.updated_by != user.id` 判定「该波次包含他人角色」。而前端 `SlotCell` 的可编辑判定用的是 `slot.owner_id === currentUserId`。管理员替别人调整后 `updated_by` 变为管理员，导致该玩家界面上看得到「撤下/改职责」却收到 403 —— 前后端不一致（现状已存在，本功能会使其常态化）。

修正：非管理员的格子归属判定**统一改为按角色归属**（格内角色的 owner == 当前用户），涉及三处：

- `remove_slot`：`slot.character.user_id != user.id → 403`
- `change_duty`：同上
- `delete_wave`：`any(s.character.user_id != user.id for s in filled) → 403`

`updated_by` 字段保留在数据模型上，仅作审计，不再用于权限判定；无需数据迁移。

## 4. 前端改动

### 4.1 `CharacterPickerModal` 扩展（管理员模式）

- 新增 prop / 内部判定：管理员走「全玩家」模式，普通玩家走原 `/api/me/characters`（逻辑不变）
- 管理员模式：
  - `onMounted` 拉 `GET /api/admin/characters`
  - 顶部**玩家选择器**（Naive UI `n-select`，可搜索昵称/角色名），默认选中当前管理员自己；**若管理员自己没有角色，则默认选第一个有角色的玩家**（空列表兜底显示「该玩家暂无角色」）
  - 下方列出所选玩家的角色（复用现有角色条目样式：职业图标、名望、模拟/秒伤或增益）
  - 选中角色 + 职责下拉 → 确定，emit 现有 `select` 事件

### 4.2 `SlotCell` 新增交互（管理员）

- 已占位格：管理员视角**可点击**（光标提示），点击 emit `manage` 事件打开操作菜单
- 新增展示属性：`is-admin`（管理员）、`moving`（是否移动源）、`move-target`（是否可作为移动目标，进入移动态后除源格外所有格高亮）
- 普通玩家视觉与交互不变

### 4.3 操作菜单（紧凑小弹窗，与现有 NModal 风格一致）

管理员点击已占位格弹出，显示当前格角色摘要 + 三个操作：

- **换人** → 打开选人弹窗（管理员模式），确认后调用 fill 接口（对已占位格，自动换人）
- **拿起** → 进入移动态（设置 `movingSlot`）
- **撤下** → 现有 remove 接口

### 4.4 移动状态机（`RaidDetailView`）

- 新状态 `movingSlot: Slot | null`
- 「拿起」后：
  - **移动态下格子点击走 move，不再弹操作菜单**；唯一例外是**再点一次源格 → 取消移动态**（不发起 move-to-self 请求）
  - 所有 slot 渲染为可落目标（源格特殊高亮「移动中」）
  - 点击目标格：
    - 空格 → 调 `move` 接口（move）
    - 占位格 → 调 `move` 接口（swap）
  - 点页面空白 / 按 Esc → 取消移动态
- `move` 接口成功或失败后均退出移动态、刷新（复用现有 `load()` 模式）
- 移动态下普通玩家不受影响（移动态仅管理员可进入）

### 4.5 前端 API 客户端

- `api.ts` 新增：`getAllCharacters()`、`moveSlot(rid, fromSlotId, toSlotId)`
- WS 事件复用现有 `applyEvent`（`slot:filled` / `slot:removed`），无需新增事件处理

## 5. 校验与边界

| 场景 | 结果 |
|---|---|
| 管理员 fill 已占位格（换人） | 原角色自动撤下，新角色放入；组成规则校验通过才生效 |
| 普通玩家 fill 已占位格 | 400「该格已有人占位」（现状） |
| 普通玩家 move 接口 | 403 |
| 源格为空时 move | 400 |
| move 目标格跨攻坚 | 404「格子不存在」 |
| 跨波 move 后目标波该玩家已有角色 | 400「同一波次中一个玩家只能上一个角色」 |
| 跨波 swap 双向任一方造成同玩家同波两角色 | 400（同上） |
| swap 同波两格 | 集合不变，放行 |
| 目标小队满员无划水 + 组成问题 | 400（复用现有硬性规则） |
| 目标小队主奶超限 | 400（恒硬性） |
| 锁定状态 | 管理员可 fill/move；普通玩家被阻（现状） |
| 管理员替玩家调整后，该玩家撤下/改职责自己角色 | ✅ 放行（3.4：按角色归属 owner_id 判定） |

## 6. 测试

- **后端 pytest**：
  - `fill`：管理员换人（占位格直接放）、管理员用他人角色、普通玩家限制不变
  - `move`：move 成功、swap 成功、跨波 move、跨波同玩家冲突 400（含 swap 双向）、源格空 400、目标格=源格 400、跨攻坚 404、非管理员 403、主奶超限回滚、满员组成问题回滚、WS 广播事件正确（move=1 filled+1 removed；swap=2 filled）
  - `GET /api/admin/characters`：仅管理员、返回结构正确、过滤空角色玩家
  - 3.4 权限修正：管理员放置/移动某玩家的角色后，该玩家本人可正常撤下/改职责/（波次全为自己的角色时）删波次
- **前端 Vitest**：
  - 移动状态机 composable/函数（拿起→点目标 move/swap、取消、Esc）
  - 管理员模式选人弹窗数据组装（全玩家分组）
  - SlotCell 在 is-admin / moving / move-target 下的类与事件
- 现有测试全量回归

## 7. 不做的事（YAGNI）

- 不做拖拽（drag & drop）
- 不做普通玩家的排表能力限制
- 不做「被调整玩家」的通知机制
- 不动公共机器人 API
